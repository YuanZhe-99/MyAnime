## 1.7.3 — 外壳页面与面板不再被悬浮导航栏遮挡

- **对 1.7.2 `navBarAwarePadding` 排查的补充，那次排查并不完整。** 1.7.2 的条目只覆盖了五个标签页的列表，但外壳导航器中的每个页面同样会绘制到 Expressive 底栏之后。设置页双栏布局的详情页（许可、隐私政策、WebDAV、重复检查）会把最后的内容滚到底栏下面；它们现在用 `navBarAwarePadding` 包住内边距，而 `SingleChildScrollView` 会把 `EdgeInsets.zero` 传入其中，因为只有内边距为 null 的 `ListView` 才会自己加上这份内边距。`ShellRoute` 之外的路由与 `rootNavigator: true` 的推入本来就位于底栏之上。
- **动漫操作面板覆盖底栏。** 它现在以 `useRootNavigator: true` 打开，不再在底栏下方打开。`navBarAwarePadding` 的文档也已更正：它适用于外壳导航器中的每个页面，而不只是各标签页。

## 1.7.2 — 紧凑的 Expressive 导航、导航位置与头像编辑器

- **紧凑的 Expressive 导航栏。** `shell_scaffold.dart` 中的 `_FloatingNavBar` 被 `_ExpressiveNavBar`（以及 `_ExpressiveNavItem`）取代：宽度就是各项的宽度、居中、elevation 为 3、与屏幕边缘留有边距的胶囊，而不再是宽度上限 480 dp 的 `NavigationBar` 岛。选中的目的地在一个 48 dp 高的 `secondaryContainer` 胶囊里并排显示图标与标签；其余只显示轮廓图标，带提示与语义标签；选中切换带 250 ms 动画。`floatingNavBarIsland` 这个 key 不变。该栏现在**悬浮在页面之上**：Expressive 底栏下外壳使用 `Scaffold(extendBody: true)`，页面因此绘制到它之后，外壳还把传给其子级的 `viewPadding.bottom` 抬到底栏的高度。Material 3 保持经典栏，内容仍停在其上方。
- **页面用 `navBarAwarePadding` 留出空间。** `adaptive_layout.dart`（该文件现在导入 `flutter/widgets`）中新增的 `navBarAwarePadding(context, padding)` 把 `MediaQuery.paddingOf(context).bottom` 加到列表的内边距上。它包住每一处 `shellListBottomInset` 内边距：管理页的四个列表、统计页的主列表与假名页的主列表；首页与设置的列表没有显式内边距，会自动获得这份内边距。`shellListBottomInset` 的 80 现在被明确记录为仅是 FAB 的避让空间。
- **FAB 修复。** 页面自己的 `Scaffold` 按 `viewPadding` 而不是 `padding` 摆放 FAB，因此内容绘制到底栏之后时，FAB 起初落在底栏后面。外壳的 `MediaQuery` 包装把 `viewPadding.bottom` 抬到 `padding.bottom`，FAB 因此高于底栏。
- **导航位置。** 一项设备本地设置 `AppSettings.navPlacement`（`NavPlacement { bottom, sideOnWide, side }`，声明于 `theme.dart`；**设置 › 通用 › 导航栏位置**，两种界面风格通用）决定导航放在哪里：**全部底部**（默认：每个窗口都用底栏）、**宽屏侧边**（按 `useNavigationRail` 使用侧边导航栏，与 1.7.2 之前相同）或**全部侧边**（每个窗口都用侧边导航栏，包括手机；不推荐）。**这改变了默认值：**1.7.2 之前宽窗口总是使用侧边导航栏，现在除非更改位置，Material 3 在宽窗口上也显示标准的 `NavigationBar`。`navRailOnRight`（**侧边导航栏位置**，位置不是全部底部时显示）在两种风格下都把侧边导航栏放到右侧。`showRail = switch (placement) { bottom => false, sideOnWide => wide, side => true }`。它们存储在 `storage_config.json` 中，键为 `navPlacement: "sideOnWide" | "side"`（缺省表示底部；未知的值按底部读取）与 `navRailRight: true`；两者都不同步。**已知的近似：**`shellContentWidth` 与其他宽度辅助函数仍按 `useNavigationRail(width)` 计算，因此宽窗口上使用底栏时它们会低估内容宽度约 81 dp（安全一侧），手机上使用侧边导航栏时则会高估侧边导航栏那么宽的内容宽度。
- **头像编辑器。** 所选图片不再被自动居中裁剪：它会在全屏编辑器（`showAvatarEditor` / `AvatarEditorPage`）中打开，在圆形遮罩内拖动与缩放（1 倍到 8 倍）、按四分之一圈旋转与重置，*保存*会把恰好取景的正方形存为 512 px 的 JPEG。个人资料对话框新增了*调整头像*按钮，并让头像可点按，二者都会在已存储的头像上重新打开编辑器。图像操作移到新的 `avatar_image.dart`（`prepareAvatarSource`、`cropAvatarJpeg`、`squareAvatarJpeg` 与各个 `...InBackground` 包装函数）；`ProfileStore.pickAvatar()` 被 `pickAvatarSource()`、`readAvatarBytes()` 与 `setAvatarJpeg(jpeg)` 取代，`ProfileNotifier.pickAvatar()` 被 `setAvatarJpeg(Uint8List)` 取代。
- **GUI 测试中发现并修复的 isolate 缺陷。** 第一版把图像处理写成在 `State` 方法里创建的闭包，而它会同时捕获该 `State` 及其控制器，无法发送到另一个 isolate。`prepareAvatarSourceInBackground` 与 `cropAvatarJpegInBackground` 现在是顶层函数，其闭包只捕获各自的参数。
- **一处既有的不稳定测试修复。** 十四个 UI 测试文件用 150–300 ms 的真实时间循环（3–6 × 50 ms）等待界面稳定，在并行负载下会失败；全部加宽为 20 × 50 ms。
- 测试从 639 个增至 655 个通过（3 个跳过）；`shell_nav_ui_test` 覆盖紧凑栏的标签与提示、内容滚动到底栏之后且最后一行与 FAB 高于底栏、Material 3 保持内容在其底栏之上、两种风格下的每种导航位置，以及右侧的侧边导航栏；`profile_test` 覆盖 `prepareAvatarSource`、`cropAvatarJpeg`（区域与限制）、在 isolate 中运行的后台辅助函数，以及 `setAvatarJpeg` / `readAvatarBytes`。`flutter analyze` 无任何问题。已在 Windows 调试版上验证，包括编辑器的完整流程（选择、旋转、保存）。版本 1.7.2+71；安装包/MSIX 版本 1.7.2.0。

## 1.7.1 — Material 3 或 Expressive

- **界面风格设置取代悬浮栏开关。** **设置 › 通用 › 界面风格**是一个 `SegmentedButton<AppUiStyle>`，有 *Material 3* 与 *Expressive*（默认）两项，布局与主题选择器一致；它取代了 1.7.0 的*悬浮导航栏*开关。悬浮岛现在属于 Expressive，Material 3 使用经典的通栏底栏（`ShellScaffold` 只在 Expressive 时显示 `_FloatingNavBar`；宽窗口的侧边导航栏在两者下相同）。`AppSettings.uiStyle` / `setUiStyle` 取代 `floatingNavBar` / `setFloatingNavBar`，`AnimeStorage.getUiStyle` / `setUiStyle` 取代 `getFloatingNavBar` / `setFloatingNavBar`；l10n 键 `settingsFloatingNavBar` 与 `settingsFloatingNavBarDesc` 换成了 `settingsUiStyle`、`settingsUiStyleDesc`、`settingsUiStyleMaterial3` 与 `settingsUiStyleExpressive`。
- **Expressive 在主题层面改变了什么。** `AppTheme.build` / `light` / `dark` 增加 `style` 参数（默认 `AppUiStyle.expressive`），`_expressive` 在与 1.7.0 完全相同的主题之上叠加：更大的圆角（卡片 20、对话框 32、底部面板上缘 32、菜单 16、Chip 12、FAB 20、描边文本框 12）；按下时从胶囊形变为圆角方形的按钮（200 ms）；加重的 display、headline 与 title 字重（字号与行高不变）；2024 版的进度指示器与滑块设计；Android、Fuchsia、Linux 与 Windows 上的淡入前进式页面转场（iOS 与 macOS 仍用 Cupertino）；以及圆角 16 的悬浮 snack bar。**它不做的事：**弹簧动效、波浪形指示器、按钮组、分体按钮、FAB 菜单和悬浮工具栏都不模仿，因为 Flutter 没有 Expressive 组件——这是一种近似，而不是 Material 3 Expressive 本身。两种风格的配色完全相同，布局从不改变。
- **设置会被沿用。** 设备本地的 `storage_config.json` 键 `uiStyle` 只存储 `"material3"`；缺省表示 Expressive。关闭过悬浮栏的 1.7.0 安装（`classicNavBar: true`）保持经典外观：`getUiStyle` 把该键读取一次并视为 Material 3，下一次 `setUiStyle` 写入时将其移除。
- 测试从 631 增至 639 个通过（3 个跳过）；新的 `theme_style_test` 覆盖共用配色、默认风格、原版 Material 3、Expressive 的形状、字重、悬浮 snack bar、文本框圆角与按下变形，以及存储的默认值、`classicNavBar` 沿用和写入语义，`shell_nav_ui_test` 现在使用 `uiStyle`。`flutter analyze` 无任何问题。版本 1.7.1+70；安装器/MSIX 版本 1.7.1.0。

## 1.7.0 — Material 3、悬浮导航栏与同步的个人资料

## 1.6.5 — 折叠屏分集页、播放器控件与同步的播放进度

- **分集页采用共享的分栏规则。**在 `canSplitLayout` 允许的窗口上，季数对应表单位于左栏，正片与特典在右栏按至少 360 dp 的列宽分列；手机和竖屏折叠屏保持一列。此前因内边距直接设在列表本身而丢失的底部安全区内边距已恢复。
- **所有平台使用应用自己的播放器控件**，取代 media_kit 自带的控件：单击显示或隐藏，双击播放或暂停，水平滑动预览目标、松手时跳转（滑过整个宽度至多 90 秒），长按期间加快一档播放（当前速度 + 1.0，至多 3.0）、松手恢复，−5 秒 / +5 秒按钮，播放速度菜单（0.25、0.5、1.0、1.5、2.0、3.0）在本次会话的各集之间沿用，进度条，全屏，以及桌面快捷键（Space、← / →、F、Esc）。media_kit 的唤醒锁和后台暂停行为不变。
- **同步的播放进度。**新的第三个数据模块 `playback_progress.json` 保存每一集的续播位置；它会同步、会备份、包含在 ZIP 导出中，并有自己的 `.sync_base`。低于 5% 时不写入；超过 95% 时删除该位置。合并从不冲突：每个键以较新的位置为准，看完的集保持删除。每次同步多一个 `GET`；重新录制了 WebDAV 请求的 golden 文件。
- **行为变更，已于 2026-09-26 与用户确定：播放超过带编号一集的 95% 即把它标记为已看**（写入新的 `modifiedAt`，与已看开关相同）。1.6.4 及之前，播放从不改变观看状态。它仍然从不自动播放下一集。分集页的自动首次播放现在会续播最近停止的未看集。

- `v1.5.0`：后台资料更新。此前保持资料库信息最新完全是手动的——打开一条记录、点「刷新资料库信息」，一次一部。新增的 `MetadataUpdateService` 在应用打开期间运行两条队列，划分依据是**字段属于谁**：`externalMeta` 是别人公开数据的本地副本，因此已经知道来源的记录会被静默刷新；`title`、`endEpisode`、`firstAirDate` 等属于用户，因此任何会改动它们的内容都变成一条**建议**，从管理页的角标进入审阅——可逐字段、逐记录、逐管理页，或经两道确认对全库应用。**承重的决定是后台写入绝不碰 `modifiedAt`。** `mergeRecords` 判断一条记录是否变化，只比较 `modifiedAt` 与同步基线，从不比较内容，因此在后台更新它会让在另一台设备上删除的记录复活（「远端删除后本地又改过 → 保留」），并为无人做出的编辑弹出冲突对话框；不动它会让 `localChanged` 恒为 false，使两者都不可能发生，而刷新到的数据仍然会传播、仍然会上传。详情页原有的手动刷新 chip 带有同样的隐患，已一并移到 `AnimeStorage.patchExternalMeta` 这条路径上。新测试揪出的一个陷阱：`Anime.copyWith` 在省略该参数时会把 `modifiedAt` 填成当前时间而不是保留原值，因此两个调用点都必须显式把旧值传回去——`patchExternalMeta` 的第一版没有这样做，那会让整个设计彻底失效；现已有回归测试锁定它。集数不一致只在 `startEpisode == 1` 时才报告，因为把后半季记成第 13–24 集的分割档记录，其 `totalEpisodes` 为 12 而来源报 24，这本身是合理的；少了这条守卫，本功能会专挑用户最用心整理的那些记录刷假警报。`diffCandidate` 绝不建议覆盖非空的用户值，唯一的例外是集数确实对不上时的 `endEpisode`，这正是「全部更新」得以成立的依据；置信度规则无法分辨的一律归档为 `needsManualPick` 并排除在所有批量操作之外。限流远低于各来源公布的限制（刷新间隔 5 秒、搜索间隔 15 秒），退避为 1 时 → 6 时 → 24 时 → 7 天，而且**离线被刻意不计为失败**，使一趟地铁不会把整个资料库推进七天退避。新增 `connectivity_plus` 依赖按链路类型门禁：桌面默认开启，Android 与 iOS 默认为「不使用蜂窝数据」——文案如此措辞，并在文档中被记为启发式而非保证，因为该插件报告的是传输方式而不是是否计费（手机热点同样报告 Wi-Fi）。已下载的候选与尝试/退避状态存放在新的设备本地文件 `metadata_updates.json` 中，既不同步也不备份——这不需要任何特殊处理，因为两个引擎都只碰 `ModuleRegistry` 中注册的文件。封面预下载是一个独立的、默认关闭的开关，它是这份缓存唯一可能容纳的大体积数据。同时删除了外部评分分区下「来自外部资料库，与你自己的评分相互独立」这句说明：卡片标题、分区标题与每个来源的 chip 标签本就承担了这个区分，这句话只是用文字重述了版面已经展示的内容。另外顺手修复了一个既有 bug：`addOrUpdate` 与 `deleteAnime` 会丢弃 `AnimeData.extraJson`，因此由更新版本写入的未知顶层字段会被任何旧版本的编辑丢掉，这与本仓库自己的向前兼容规则相悖。另有三个缺陷是靠驱动真实应用而非测试套件发现的：每条记录都被抓取了**两次**，因为已完成的刷新停留在尚未落盘的写入缓冲里，于是从磁盘看它仍然像是从未抓取过（缓冲是用来批量写盘的，不能让队列忘记自己刚做过什么）；英文批量对话框显示为「Apply all 1 updates?」与「This changes 1 records at once」——计数是 int，因此这种不合语法的写法能正常编译，且只在恰好一条记录时暴露，而那正是最常见的批量规模，现已用 ICU 复数修正并由本地化测试锁定；以及 `needsManualPick` 卡片在「No match was clear enough」正上方显示「100% match」，自相矛盾——标题确实得了 100 分，但另一部**作品**的分数几乎相同，因此现在只有在真正提议候选时才显示匹配度。测试数 105 → 143。版本统一为 `1.5.0+53` / MSIX `1.5.0.0` / 安装包 `1.5.0`。
- `v1.5.1`：更新页的入口、用户可以主动要求的检查，以及两处进度。1.5.0 交付的后台流水线只有被动的那一半：管理页的角标按钮以 `_pendingUpdateCount > 0` 为条件，因此没有待确认项时按钮根本不存在——而它背后的审阅页又是唯一能发起检查的地方。这让「还什么都没有」的那批用户（包括所有把网络策略设为 `off` 的人）完全无从进入。现在完整版中这个入口始终存在，来去的只有角标；审阅页则在 AppBar 上、以及作为空状态的主按钮，各带一个**检查更新**操作。这次检查走的是 `buildScanQueue` 构造的快照队列，在开始时即固定，因此进度条的分母永不变动、循环也一定会终止。它无视什么、尊重什么就是整个设计：失败退避与 30 天重新探索窗口被**无视**，因为「立刻重试」正是这个按钮的含义，而那两者只是「别太快重试」的启发式；用户的忽略被**尊重**，因为重新提议一次拒绝会让*忽略*失去意义；缓存新鲜度被**尊重**，因为对 200 条的库重新抓取仍新鲜的资料要花上几分钟、上千次请求却什么都不会改变；而 `metadataAutoUpdate` 策略被**无视**，因为该设置管的是*无人值守*的流量，这里则是用户可以看着、可以随时停止的一次明确点击——并且当策略为 `off` 时，这个按钮是唯一的检查途径。离线仍然拒绝执行，因为那样每一项都会失败、白白把整个库推进退避；为此需要把 `_isOffline` 从 `_networkGate` 中拆出来，后者一旦策略为 `off` 就会短路返回 `blocked`，而那恰恰是手动按钮必须能工作的场景。手动间隔比后台更紧，因为用户正在看着（刷新 2 秒、搜索 6 秒），并且仍受同一套算术约束：一次刷新对单一站点最多 1 次请求、一次 `searchAll` 最多 2 次，因此分别为每分钟每站点 ≤30 与 ≤20 次，而 Jikan 是 60、AniList 是 90。执行期间后台定时器会被取消——两个 worker 打同一批 API 会让速率变成这些间隔所设定值的两倍。队列为空时报告的是*所有资料都已是最新*而不是*未发现可用更新*：这是两个不同的结论，而当「没有检查任何东西」的原因是「没有东西需要检查」时，只有前者是真的。取消会让已发出的那次请求跑完，并保留已找到的结果。其次，**搜索对话框不再只显示一个光秃秃的转圈**。一次检索确实可能耗时约半分钟——每个来源各有 10–15 秒超时，且空手而归的来源会用首轮采集到的标题再查一次——在这段时间里，孤零零一个转圈与真正的卡死无法区分。`searchAll` 现在接受一个可选的 `onProgress` 回调，在每轮开始与每个来源作出回应时上报 `AnimeSearchProgress`，渲染为一条确定进度条外加每个来源一个 chip。每一轮保持**各自的分母**，因为第二轮只重查空手的来源，若用单一总计，分母会在检索途中变大、把进度条往回推。失败的来源计入「已回应」，但仍与「没找到」的来源保持可区分，因为对于正在决定要不要重搜的人来说这是两个不同的答案——`_runRound` 本就会吞掉各来源的异常以免一个失效来源拖垮整次检索，所以上报正是从同一个处理分支发出的。第三，`needsManualPick` 的建议新增了**手动搜索**操作，它会打开该记录的编辑页，搜索对话框已经展开且标题已填好，复用该页现有的搜索并应用路径，而不是新增第二条「用搜索结果写入记录」的通路。这要求先把审阅页正确地路由化：它此前是以命令式 `MaterialPageRoute` 推入的，而 Flutter 的 `Navigator` 会把基于 `pages` 的路由排在命令式推入的路由**下面**，因此从它内部发起的 `context.push` 会把编辑页打开在启动它的那个页面底下。现在它是一条 `/metadata-updates` 的 `GoRoute`，页面作用域通过 `extra` 传递。测试数 143 → 158。版本统一为 `1.5.1+54` / MSIX `1.5.1.0` / 安装包 `1.5.1`。
- `v1.5.2`：能用上宽屏的详情页，以及能用上别人分数的排行。**详情页的分栏是宽高比规则而非宽度断点，原因正是 Galaxy Z Fold 8。** 最显而易见的实现——在某个 `sw600dp` 式阈值之上分栏——恰恰在促成这项工作的那台设备上是错的：Fold 8 展开后是 4:3 的**横向**面板（2448 × 1848 px），因此竖屏时为 3:4，**比它所取代的近方形 Fold 7 更窄**（1848 px 对 1968 px），而 Fold 8 Ultra 却反向做到了 2256 px。如今一代产品展开后横跨约 672 到 954 逻辑像素，且同一台设备在同一宽度下需要两个不同答案：横屏双栏，竖屏保持原本的单栏。于是 `useDetailTwoPane` 检查三件事——宽度 ≥ 600、高度 ≥ 480、宽高比 ≥ 0.82——其中宽高比检查是承重的那一项，位于 Fold 8 竖屏 0.755 与 Fold 7 / Fold 8 Ultra 竖屏 0.90 之间空隙的中段。`kana_page.dart` 中已在使用的 720 阈值会直接让 Fold 8、Fold 5 和 Fold 6 落选；840 则只剩 Ultra。高度下限并非与宽度下限重复：仅凭宽高比检查会放行**又宽又矮**的视口，没有它，折叠状态的 Fold 8 封面屏旋转到横向（约 657 × 416 dp）和普通手机横屏（约 915 × 412 dp）都会被拆成两个逼仄的栏。由于该规则针对形状而非设备类别，4:3 和 16:10 的平板与 Fold 8 完全一致——横屏双栏，竖屏单栏。该判断读取 `MediaQuery.sizeOf` 而非用于给两栏定尺寸的 `LayoutBuilder` 约束，因为以 `Scaffold` body 度量会扣掉应用栏并抬高比值，使 Fold 8 3:4 面板相对宽度的纵向空间过于充裕，只按高度定尺寸会得到又高又窄的封面。其次，**排行视图现在可以按资料库评分而非你自己的评分排名。** 外部分数自 1.4.0 起就按来源存放在 `externalMeta.ratings` 中，而统计页从未读取过它们。承重的细节在于 `scoreMax` 是**逐条记录**存储的，因此任何跨来源比较都必须除回去——直接读 `score` 会把 bangumi.tv 的 7/10 排在 MyAnimeList 的 85/100 之上——于是有了评分上的 `normalizedScore`、元数据上的 `normalizedScoreFor` 与 `averageNormalizedScore`，并带 `scoreMax <= 0` 守卫，使格式错误的记录无法算出排到榜首的无穷大。跨来源平均是默认值，也可锁定单一来源；平均之所以是更稳健的默认，是因为一条记录恰好带有哪些来源因番而异，而锁定单一来源会静默剔除所有缺少该来源的动画。切换来源真正改变的是**哪些**动画出现，而不只是顺序——按自己的评分会剔除全部未评分的，按资料库会剔除全部从未抓取过的——因此过滤器与比较器被收拢到唯一的 `_rankingScoreOf`
