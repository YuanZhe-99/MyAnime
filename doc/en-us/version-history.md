# Version history

Release-by-release summary of MyAnime!!!!!. Useful for understanding *why* a behavior exists before
changing it — several entries record deliberate safety fixes that look like quirks otherwise.

## Repository caveat

The latest release tag before the documentation guide was added was `v0.6.7`, with `origin/master`
and `github/master` aligned there. Early history has one wrinkle: two root commits share the same
content after an early `git commit --amend`, and tag `v0.1.0` points to the later root. **Avoid
`git commit --amend` on root commits.**

- `v1.3.1`: Fixed the custom storage-path migration. Changing the storage folder previously moved only `anime_data.json`, stranding `images/`, `.sync_base/`, `backups/` (bundles and blobs), and `webdav_config.json` at the old location. The worst consequence was silent: without `.sync_base/` the next sync has no base snapshot, so records other devices had deleted read as "new locally" and were re-uploaded, resurrecting deletions across every device; losing `webdav_config.json` also stopped sync entirely, which disabled the image sync that would otherwise have repaired the missing covers. Migration now moves the **entire** storage folder except `storage_config.json` (which must stay put — it holds the path itself), so a data file added in a future release migrates with no code change. Existing destination files still win, and their source copies are now left in place rather than discarded. Shared logic lives in `myapps_data` `v1.0.1` as `migrateStorageContents`, covered by eight tests. Versions unified to `1.3.1+49` / MSIX `1.3.1.0` / installer `1.3.1`.

- `v1.3.3`: Local archive tracking. Each anime gains an optional `localArchive` record — whether a downloaded local copy is kept, its source medium (`BD`/`DVD`/`WEB`/`TV`/other) and resolution (`2160p`/`1080p`/`720p`/`480p`/other) as two independent axes so `BD 1080p` and `WEB 1080p` stay distinguishable, how many copies exist, and a free-text repository code or location (several codes can share the one field). It is edited in a collapsible section of the edit page modeled on the rating section, shown as a read-only card on the detail page, and filterable on the management page through a three-state AppBar filter (all / archived / not archived, where "not archived" folds together "never recorded" and "explicitly not kept", since the question is what still needs downloading). **WebDAV sync required no code change at all**: `anime_data.json` is merged whole-record by `mergeRecords<Anime>` keyed on `id` + `modifiedAt`, so teaching `toJson`/`fromJson` about the field was sufficient, and `data_modules.dart`, `sync_merge.dart`, and `webdav_service.dart` were left untouched. `AnimeLocalArchive.hasAnyData` gates serialization so an anime that never used the feature emits no `localArchive` key and serializes byte-identically to before — the WebDAV request goldens still pass unmodified, which is the proof the wire format is unchanged. Because the values name the user's own storage infrastructure rather than their viewing habits, the field is synced but never shared: it is stripped from `.myanimeitem` exports alongside `episodeStatuses`/`episodeWeekOffsets`, and never drawn into image cards (the three canvas renderers read named properties, so exclusion is the default). It *is* exposed as an additive key on the loopback, Basic-Auth-protected local HTTP API. Duplicate merge takes the record whole from the first source that has one rather than field-by-field, since mixing a `source` from one record with a `location` from another would describe a copy that does not exist. Enum labels live in a new shared `lib/features/anime/views/archive_labels.dart` rather than being duplicated per page, with `BD`/`1080p`-style technical tokens hardcoded and only "other" localized. Versions unified to `1.3.3+51` / MSIX `1.3.3.0` / installer `1.3.3`.
- `v1.4.0`: Search overhaul — richer metadata, a usable result list, and cross-language queries. **Pulling more:** the sources were already returning far more than the app read. AniList's GraphQL document had requested `airingSchedule` since v0.3.0 but the parser never touched it, so the broadcast weekday was *guessed* from `startDate.weekday` — wrong for any series whose premiere aired off its regular slot; it now comes from `nextAiringEpisode.airingAt` (falling back to the first schedule node, queried without `notYetAired` so finished shows still resolve), converted to Japan time. bangumi.tv's `air_weekday` and rating block were likewise sitting unread in every response. Jikan now contributes `titles[]`, studios, genres, duration, format, status, and score — and only trusts `broadcast.time` when `broadcast.timezone` says `Asia/Tokyo`, instead of labelling a non-Tokyo time as JST. Per-source caps went from 5 to 10. Late-night slots are filed under the previous day in `25:00` form, following the Japanese 04:00 programming-day boundary the app already assumes: a 01:00 Thursday airing becomes Wednesday `25:00`. This is load-bearing because `getEpisodeCalendarDate()` ignores `airTime` entirely and places an episode from `firstAirDate` + `airDayOfWeek` alone, so the weekday and the first-air date are shifted **together** — shifting only the weekday would leave the two disagreeing and the forward-snap would push episode 1 a whole week out. **Storing it:** a new `externalMeta` record (`AnimeExternalMeta` + `AnimeExternalRating`) holds alternate titles, romaji/English titles, format, status, duration, genres, studios, end date, and one rating entry per source. External scores are kept strictly apart from the user's own `AnimeRating` — nothing writes one into the other — and each rating remembers the `sourceUrl` it came from, which is what makes refreshing possible: a detail-page action re-fetches every remembered page by id (AniList `Media(id:)`, Jikan `/full`, bangumi `/subject/<id>`, all through the *same* mappers the search path uses) and folds the results in, taking each field only when the new fetch actually supplies it so refreshing against one source never erases another's contribution. Unlike `localArchive`, this is public information about the work, so it travels in `.myanimeitem` share files. WebDAV needed no change again — whole-record merge plus `hasAnyData`-gated serialization. **Two dead sources, found by testing against the real APIs.** bangumi.tv had been on the legacy `GET /search/subject/` endpoint since the first release; it now returns `502 Bad gateway` from Cloudflare for every request, and because each source method treats a failure as an empty result, bangumi.tv had silently dropped out of search entirely with no error surfaced anywhere. It moved to the v0 API (`POST /v0/search/subjects`, `GET /v0/subjects/{id}` — plural), which is alive and returns strictly more: `infobox` carries the broadcast weekday, alternate titles, studio, and end date, none of which the legacy search response had. Separately, filmarks.com moved its detail URLs from `/anime/<id>` to `/animes/<series>/<season>` and now renders results client-side, so the `/anime/` patterns unchanged since v0.1.0 matched nothing; the scraper was rewritten against the current markup, taking the title from the poster `alt`. The lesson is recorded in the source docs: a source can disappear without anyone noticing, so a sudden zero-result run means suspect the source before the query. **Cross-language search:** `searchAll` now runs two rounds. Round one sends each source the variant it indexes best (Simplified to bangumi.tv, Traditional to acgsecrets.hk, `Accept-Language: ja` to filmarks.com), replacing the old bangumi-only Simplified special case. Round two harvests up to three high-confidence titles (Japanese, romaji/English, Chinese) from round one and re-queries *only* the sources that came back empty — which is what finally lets a Chinese query reach filmarks.com, a Japanese-title-only site. One extra round, never recursive. Results are deduplicated and ranked by a public `relevance()` that scores every known title of a result, so ranking is language-neutral. **Result UI:** sort (relevance / first air date / episodes / source, with missing values always sinking rather than sorting as zero), filter (source chips, has-cover, has-air-date), group-by-source, and long-press — a row's title is clipped to one line, and long-pressing opens a sheet with every title as selectable, copyable text plus all fetched metadata; desktop gets a hover tooltip. The local API gained the new fields additively, an optional `language`, and a `limit` defaulting to 10. Six source-format parsers are exposed `@visibleForTesting` and covered by 18 new tests, since the HTTP calls are static and offer no injectable seam. The `functions/INDEX.md` totals were recomputed against the real source tree: they claimed 682/685 while the per-file rows summed to 615 and the tree actually held 622 `Purpose:` comments, and the corrected figures now carry a note about the remaining coverage gap. Versions unified to `1.4.0+52` / MSIX `1.4.0.0` / installer `1.4.0`.
- `v1.5.0`: Background metadata updates. Until now, keeping database info current was entirely manual — open a record, press "refresh database info", one anime at a time. A new `MetadataUpdateService` runs two queues while the app is open, split by **who owns the field**: `externalMeta` is a local copy of someone else's public data, so records that already know their source get it refreshed silently; `title`, `endEpisode`, `firstAirDate` and the rest belong to the user, so anything that would change one becomes a **proposal** reviewed from a badge on the management page — one field at a time, per record, per management page, or library-wide behind two confirmations. **The load-bearing decision is that background writes never touch `modifiedAt`.** `mergeRecords` decides whether a record changed purely by comparing `modifiedAt` against the sync base and never by comparing content, so bumping it in the background would resurrect records deleted on another device ("modified locally after remote deleted → keep") and raise conflict dialogs for edits nobody made; leaving it alone keeps `localChanged` false, which makes both impossible while the refreshed data still propagates and still uploads. The detail page's existing manual refresh chip carried the same hazard and was moved onto the same `AnimeStorage.patchExternalMeta` path. A trap found by the new tests: `Anime.copyWith` stamps `modifiedAt` with the current time whenever the argument is omitted rather than preserving it, so both call sites must pass the old value back in explicitly — the first version of `patchExternalMeta` did not, which would have defeated the entire design; a regression test now pins it. An episode-count mismatch is only reported when `startEpisode == 1`, because a split-cour entry tracked as episodes 13–24 legitimately has `totalEpisodes == 12` against a source reporting 24, and without that guard the feature would have raised false alarms on exactly the records a user curated most carefully. `diffCandidate` never proposes overwriting a non-empty user value, with `endEpisode` on a demonstrable mismatch as the single exception, which is what makes "update all" defensible; anything the confidence rules could not separate is filed as `needsManualPick` and excluded from every batch action. Rate limiting stays well under each source's published limits (5 s between refreshes, 15 s between searches) with a 1 h → 6 h → 24 h → 7 d backoff, and **being offline is deliberately not counted as a failure** so a subway ride cannot push a whole library into a seven-day backoff. New `connectivity_plus` dependency gates the work by link type: on by default on desktop, defaulting to "don't use cellular data" on Android and iOS — worded that way, and documented as a heuristic rather than a guarantee, because the plugin reports the transport and not whether it is metered (a phone hotspot still reports Wi-Fi). Downloaded candidates and attempt/backoff state live in a new device-local `metadata_updates.json` that is neither synced nor backed up — which needs no special handling, since both engines only touch files registered in `ModuleRegistry`. Cover prefetch is a separate, off-by-default switch, the only large data this cache would hold. Also removed the "From external databases — separate from your own rating" line under the external-ratings section: the card title, the section heading, and the per-source chip labels already carry that distinction, so the sentence restated in prose what the layout was already showing. Also fixed a pre-existing bug found in passing: `addOrUpdate` and `deleteAnime` dropped `AnimeData.extraJson`, so unknown top-level fields written by a newer build were discarded by any older build's edit, contrary to this repo's own forward-compatibility rule. Three more defects were found by driving the real app rather than by the test suite: every record was fetched **twice**, because a completed refresh sat in the unflushed write buffer and so still looked never-fetched to the queue on disk (the buffer batches writes; it must not make the queue forget what it just did); the English batch dialogs read "Apply all 1 updates?" and "This changes 1 records at once" — the counts are ints, so the ungrammatical form compiled and only surfaced at exactly one record, the most common batch size of all, now fixed with ICU plurals and pinned by locale tests; and a `needsManualPick` card showed "100% match" directly above "No match was clear enough", which is self-contradictory — the title really did score 100%, but a rival *work* scored nearly the same, so the percentage is now hidden unless a candidate is actually being offered. Test count 105 → 143. Versions unified to `1.5.0+53` / MSIX `1.5.0.0` / installer `1.5.0`.
- `v1.5.1`: An entrance to the update screen, a check the user can ask for, and progress on both. 1.5.0 shipped the background pipeline with only its passive half: the management page's badge button was gated on `_pendingUpdateCount > 0`, so with nothing pending the button did not exist — and the review screen behind it was the only place a check could be started. That left the users with nothing yet, including everyone whose network policy is `off`, with no way in at all. The action is now always offered in full builds and only the badge comes and goes, and the screen carries a **Check for updates** action in the app bar and again as the empty state's primary button. The check walks a snapshot queue from `buildScanQueue`, fixed at the start so the progress bar's denominator never moves and the loop is guaranteed to terminate. What it ignores and honours is the design: failure backoff and the 30-day rediscovery window are **ignored**, because "try again now" is what the button means and those are only "don't retry too soon" heuristics; dismissals are **honoured**, because re-proposing a refusal would make *Ignore* meaningless; cache freshness is **honoured**, because re-fetching still-fresh metadata across a 200-record library costs minutes and over a thousand requests to change nothing; and the `metadataAutoUpdate` policy is **ignored**, because that setting governs *unattended* traffic while this is one explicit tap the user can watch and stop — and when the policy is `off` this button is the only way to check. Being offline is still refused, since every item would fail and push the whole library into backoff for nothing; that required splitting `_isOffline` out of `_networkGate`, which short-circuits to `blocked` as soon as the policy is `off` — exactly the case the manual button has to work in. Manual gaps are tighter than the background ones because the user is watching (2 s between refreshes, 6 s between searches) and still bounded by the same arithmetic: a refresh is at most one request per host and a `searchAll` at most two, so ≤30 and ≤20 per minute per host against Jikan's 60 and AniList's 90. The background timer is cancelled for the duration — two workers on the same APIs would double the rate those gaps are sized for. An empty queue is reported as *everything is already up to date*, not *no updates found*: those are different answers, and only the first is true when nothing was checked because nothing needed checking. Cancelling lets the request in flight finish and keeps what was found. Second, **the search dialog no longer shows a bare spinner**. A search can legitimately take about half a minute — each source has its own 10–15 second timeout, and sources that come back empty are queried a second time with titles harvested from the first round — and over that stretch a lone spinner is indistinguishable from a hang. `searchAll` now takes an optional `onProgress` callback reporting an `AnimeSearchProgress` per round and per source answer, rendered as a determinate bar plus one chip per source. Each round keeps **its own denominator**, because round two re-queries only the empty sources and a single running total would grow mid-search and drive the bar backwards. A failed source counts as answered but stays distinguishable from one that found nothing, since those are different answers to someone deciding whether to search again — `_runRound` already swallowed per-source exceptions to keep one dead source from failing the whole search, so the report is emitted from that same handler. Third, a `needsManualPick` proposal gained a **Search manually** action, which opens the record's edit page with the search dialog already open and the title filled in, reusing that page's existing search-and-apply path rather than adding a second way to write a record from a search result. That required routing the review screen properly: it was pushed as an imperative `MaterialPageRoute`, and Flutter's `Navigator` places `pages`-based routes *below* imperatively pushed ones, so a `context.push` from inside it would have opened the edit page underneath the screen that launched it. It is now a `/metadata-updates` `GoRoute` carrying the page scope as `extra`. Test count 143 → 158. Versions unified to `1.5.1+54` / MSIX `1.5.1.0` / installer `1.5.1`.
